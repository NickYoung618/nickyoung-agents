## 打开与验收

`POST artifacts/:id/start` 只启动或返回当前使用实例，不执行场景步骤。`POST artifacts/:id/verify` 从对应 Git 提交建立新的临时目录和服务实例，独立运行浏览器场景；使用实例、端口及用户数据不参与验收。相同成果的并发验收合并为同一轮，最多两轮同时运行；可通过 `cancel-verify` 停止。失败、取消、超时均关闭浏览器、停止进程组并移除临时验收目录。重启后标记未完成验收为中断，旧能力链接失效。

使用预览与验收各有最多两个实例；使用租期默认 20 分钟，`config.previewTimeout` 可调整毫秒租期。Node 文件权限、128MB 堆、浏览器 opaque origin 和管理 API 隔离继续保留。健康检查只表示服务可连接；成果可使用的状态还要求本版本场景验收通过。

## 成果卡与草稿

卡片以会话、成果 ID、版本标识，状态、证据和按钮分别局部更新。原 textarea、文件选择器和 iframe 节点保留，原实例的能力 URL 不变时不设置 iframe src。添加其他卡片和报告不整体替换成果容器。

文字和展开状态保存到本地草稿；截图在当前页面保留，刷新后明确提示重新选择，可主动移除。失败保留内容，响应丢失后使用相同请求标识重试；收到成功响应时只清理已发送的文字和同一组截图。发送期间新输入的内容保留。反馈事件和用户消息在同一 SQLite 事务内保存，按会话、成果、requestId 去重，不将仅收到请求当成已开始修改。

临时能力 URL 只由认证后的成果接口返回，不写入事件和本地草稿；验证错误会去除临时能力路径。

## 未完成工作检查点

`work_checkpoint` 记录对应任务的 HEAD、自身未提交文件内容及需要保留的用户文件。实际进程事件、停止请求和任务进程关闭后保存检查点，重复内容不重复记录。

- 模型自身未提交改动：继续、返修、改派和服务恢复可在原内容上执行，不要求用户提交中间状态。
- 暂停后同一文件变化或 HEAD 变化：保留内容，列出冲突文件，进入等待用户处理。用户明确选择保留当前内容作为新基础后才继续。
- 无关用户改动：保持原内容，告知模型不得修改，并排除交付提交；用户原有暂存内容仍留在暂存区。
- 初始未提交改动、取消任务遗留改动：不自动接管、stash 或提交，明确提示来源和处理方式。

交付只提交任务相关文件，机器检查不把被保留的用户文件认定为任务验收产生的脏文件。若模型触及保留文件，恢复保存的用户内容并列出冲突，不提交它们。检查点不会用于恢复数据库或外部服务。

如果服务在写文件与检查点落盘之间遭遇硬断电，无法证明归属的文件采用保守处理：保留文件并要求明确接管，不宣称无损自动合并。当前不提供通用三方代码合并器。

## 发布与回滚

部署脚本 `scripts/deploy-artifact-repair.mjs` 检查真实 systemd 服务目录、会话及运行中成员，遇到运行中任务会拒绝重启。备份包括 SQLite 一致副本、配置、登录材料、成果使用数据和部署前实际目录代码。`predeploy-code.tar` 保存发布时目录的实际内容，`rollback-code.tar` 保存本轮开始前已运行的 artifacts-2 代码，均不使用 `git archive HEAD` 代替实际代码。

回滚命令（路径见本次 `deployment.json`）：

```bash
node scripts/rollback-artifact-repair.mjs /绝对路径/data/backups/artifact-repair-时间
```

回滚前再次检查运行任务，并保存当前代码；仅恢复代码，数据库、登录、模型配置和成果数据保持当前内容。生产数据库备份是应急恢复材料，脚本不会覆盖数据库。

本轮提交位于独立 `fix/artifact-workbench-repair` 分支，以实际未提交实现快照作为明确的基线提交。主工作区分支和原暂存区不切换、不清空；修复提交的 diff 只包含本轮变化。部署记录保存实际代码提交，证据提交另行记录。
